الوكيل Agent

الموظف نفسه

التشبيه

موظف ليه اسم، وشخصية، وحدود صلاحيات، وقائمة بالحاجات اللي يقدر يعملها.

يعني إيه

ملف إعدادات بيحدد: أي نموذج يستخدم، إيه تعليماته، أنهي أدوات متاحة له، مين يقدر يكلّمه، وكام خطوة أقصى يعملها. مفيش كود — كله إعدادات.

مثال

app_assistant للزوار (أداتين بس)، وthree_pl_agent للموظفين (15 أداة). نفس التطبيق، وكيلين مختلفين تماماً.

غلط شائع

تعمل وكيل واحد وتحطله كل الأدوات. النماذج المحلية بتتوه بعد ~10 أدوات. قسّم حسب الجمهور.

الأداة Tool

الإيد اللي بتنفّذ

التشبيه

الموظف عايز يعرف حالة الطلب؟ لازم يفتح النظام. الأداة هي «فتح النظام».

يعني إيه

كلاس PHP عادي فيه دالتين مهمّتين: authorize() بتقول مين مسموح له، وhandle() بتنفّذ الشغل الفعلي (استعلام قاعدة بيانات، نداء API، إرسال إيميل).

مثال 
public function handle(array $input, ToolExecutionContext $context): array
{
    $order = Order::where('number', $input['order_number'])->first();

    return ['status' => $order?->status ?? 'not_found'];
}
استخدمها لما

المعلومة بتتغير: حالة شحنة، رصيد مخزون، سعر، حساب عميل. أو لما تحتاج تعمل حاجة فعلاً (تفتح تذكرة، تبعت رسالة).

غلط شائع

تكتب description غامض. النموذج بيقرأ الوصف ده بس عشان يقرر متى يستدعي الأداة — لو مش واضح، مش هيناديها.

المهارة Skill

دورة تدريبية = تعليمات + أدوات

التشبيه

بدل ما تشرح لكل موظف جديد نفس الكلام، تعمل «دورة تدريب المبيعات» وتحضّرها له.

يعني إيه

حزمة قابلة لإعادة الاستخدام بتجمع: تعليمات متخصصة + مجموعة أدوات + قواعد معرفة. تربطها بأي وكيل بسطر واحد.

مثال 
'store_public_help' => [
    'instructions' => 'لما المستخدم يذكر رقم طلب، نادِ get_order_status قبل ما ترد.',
    'tools' => ['get_order_status'],
    'knowledge' => ['store_faq'],
],
أهم قاعدة

الوكيل يشوف تقاطع الأدوات: اللي في agent.tools و في skill.tools. لو الأداة في واحد بس — مش هتشتغل خالص، والوكيل هيرد رد عام كأن الأداة مش موجودة.

قاعدة المعرفة Knowledge / RAG

الكُتيّب على المكتب

التشبيه

ملف الأسئلة الشائعة اللي الموظف بيفتحه لما حد يسأل «سياسة الإرجاع إيه؟».

يعني إيه

فقرات نصية قصيرة بتكتبها في الإعدادات. لما ييجي سؤال، النظام بيدوّر على أقرب فقرات ويحطّها في سياق المحادثة قبل ما النموذج يرد. ده اسمه RAG.

استخدمها لما

المعلومة ثابتة: سياسات، ساعات العمل، شروط، تعريفات. حاجة مش بتتغير كل دقيقة.

غلط شائع

تكتب مستند بيناقض أداة. مثلاً تكتب «لا أستطيع الوصول لبيانات الطلبات، راجع البوابة» وإنت مفعّل get_order_status — النموذج هيصدّق المستند ويتجاهل الأداة.

نصيحة

اكتب فقرات من 2 لـ 4 جمل. متحطّش PDF كامل في مستند واحد — البحث هيبوظ.

الذاكرة Memory

دفتر الملاحظات الصغير

التشبيه

الموظف بيكتب جنب اسم العميل: «بيفضّل العربي — منطقته الرياض».

يعني إيه

نوعان: ذاكرة المحادثة (يفتكر اللي اتقال في نفس الشات)، وذاكرة المستخدم (تفضيلات تفضل معاه عبر المحادثات).

الأمان

مقيّدة بقائمة مفاتيح مسموحة (allowed_keys) وحد أقصى للطول، عشان ما يتخزّنش كلام عشوائي أو بيانات حساسة.

مش للـ

تخزين بيانات أعمال. الطلبات والشحنات مكانها قاعدة البيانات وتوصلها بأداة — مش بالذاكرة.

سير العمل Workflow

إجراء رسمي بخطوات

التشبيه

«لو شحنة اتأخرت: اكتب مسودة اعتذار ← خُد موافقة المشرف ← ابعتها للعميل».

يعني إيه

خطوات مرقّمة بترتيب محدد. كل خطوة نوعها واحد من أربعة: agent (وكيل يكتب حاجة)، tool (تنفيذ أداة)، approval (استنى موافقة)، branch (لو كذا اعمل كذا).

الفرق عن الوكيل

الوكيل بيقرر بنفسه أي أداة يستخدم. الـ Workflow إنت اللي حاددله الترتيب سلفاً — استخدمه لما الإجراء لازم يمشي بنفس الطريقة كل مرة.

الموافقة والصلاحيات Approval & Authorization

توقيع المدير + بطاقة الدخول

طبقتان

الصلاحية بتقرر «هل ينفع أصلاً؟» — على مستوى الوكيل (guest_allowed) وعلى مستوى الأداة (authorize()).
الموافقة بتقرر «تمام ينفع، بس استنى المستخدم يأكّد» — بـ confirmation: true.

القاعدة

أي أداة بتغيّر حاجة في النظام (إرسال رسالة، فتح تذكرة، تعديل طلب) لازم يكون عليها confirmation: true.

الضيوف

guest_safe: true على الأداة، وguest_allowed: true على الوكيل. الاتنين لازم يتفقوا — لو واحد ناقص، الزائر هيترفض.

مخطط المدخلات input_schema

استمارة الطلب

يعني إيه

بتقول للنموذج: «الأداة دي محتاجة منك الحقول دي بالظبط». النظام بيتحقق من المدخلات قبل ما يشغّل الأداة، فمستحيل توصلك بيانات ناقصة أو بنوع غلط.

مثال 
'input_schema' => [
    'order_number' => ['type' => 'string', 'required' => true],
    'limit' => ['type' => 'integer', 'required' => false],
],

المزوّد والنموذج Provider & Model

العقل اللي بيفكر

يعني إيه

المزوّد = الشركة (OpenAI، Anthropic، Gemini، أو Ollama محلي). النموذج = الموديل نفسه (gpt-4.1-mini، qwen3:8b).

ميزة

كل وكيل يقدر ياخد مزوّد ونموذج مختلف. وكيل بسيط على نموذج رخيص، ووكيل معقّد على نموذج أقوى.

للاختبارات

LIMEN_AI_PROVIDER=fake — نموذج وهمي بردود ثابتة. اختباراتك تمشي في CI بدون أي تكلفة.

الموصّل Connector

خط تليفون لجهة خارجية

يعني إيه

لو عايز الوكيل يكلّم API خارجي (شركة شحن مثلاً)، مش لازم تكتب كلاس PHP. تعرّف الاتصال في الإعدادات، وتعمل أداة تشاور عليه.

الأمان

الحزمة بتمنع الاتصال بعناوين IP داخلية تلقائياً (حماية SSRF)، وبتخفي التوكنات من السجلات.

الحفظ والطابور Persistence & Queue

الأرشيف وغرفة الانتظار

الحفظ

بعد php artisan migrate، المحادثات والرسائل والتشغيلات بتتسجّل في قاعدة البيانات — فالمستخدم يلاقي محادثته القديمة لما يرجع.

الطابور

لو النموذج بطيء، تقدر تشغّل الرد في الخلفية بـ LIMEN_AI_QUEUE_AGENT_RUNS=true — بس ساعتها محتاج queue:work شغّال، والجلسة مش بتنتقل للعامل تلقائياً.

Schema::create('orders', function (Blueprint $table) {
    $table->id();
    $table->string('number')->unique();          // ORD-1001
    $table->string('customer_email')->index();
    $table->string('status')->default('pending'); // pending|paid|shipped|delivered
    $table->decimal('total', 10, 2);
    $table->string('tracking_number')->nullable();
    $table->date('eta')->nullable();
    $table->timestamps();
});

Schema::create('products', function (Blueprint $table) {
    $table->id();

    $table->string('name');
    $table->unsignedInteger('stock')->default(0);
    $table->unsignedInteger('reorder_level')->default(10);
    $table->timestamps();
});
2 طبقة الخدمة — منطق الأعمال app/Services/StoreService.php

php artisan make:class Services/StoreService
namespace App\Services;

use App\Models\Order;
use App\Models\Product;
use App\Models\SupportTicket;

class StoreService
{
    /**
     * @return array<string, mixed>|null
     */
    public function findOrder(string $number): ?array
    {
        $order = Order::query()->where('number', $number)->first();

        if ($order === null) {
            return null;
        }

        return [
            'order_number' => $order->number,
            'status' => $order->status,
            'total' => (float) $order->total,
            'tracking_number' => $order->tracking_number,
            'eta' => $order->eta?->toDateString(),
        ];
    }

    /**
     * @return array<string, mixed>|null
     */
    public function checkStock(string $sku): ?array
    {
        $product = Product::query()->where('sku', $sku)->first();

        if ($product === null) {
            return null;
        }

        return [
            'sku' => $product->sku,
            'name' => $product->name,
            'stock' => $product->stock,
            'is_low' => $product->stock <= $product->reorder_level,
        ];
    }

    /**
     * @return array<string, mixed>
     */
    public function openTicket(string $orderNumber, string $subject, int $userId): array
    {
        $ticket = SupportTicket::query()->create([
            'order_number' => $orderNumber,
            'subject' => $subject,
            'opened_by' => $userId,
            'status' => 'open',
        ]);

        return [
            'ticket_id' => $ticket->id,
            'status' => $ticket->status,
        ];
    }
}

1. The agent ignores your tools

The skill attached to the agent lists a different tool set. filterToolsBySkills() intersects both lists, so the agent ends up with zero tools and answers from knowledge only. Keep both lists in sync.

2. Knowledge contradicts your tools

A FAQ entry saying "the assistant cannot access private data, visit the portal" will beat your tool every time. Remove or rewrite conflicting documents when you add a tool that covers that topic.

3. Guests get rejected

Set guest_safe => true on the tool and guest_allowed => true plus required => false in the agent's authorization block. Both layers must agree.

4. Queued runs lose the user

A queue worker has no web session, so a job carrying user_id is treated as an anonymous guest and the run fails. Either restore auth on JobProcessing, or keep LIMEN_AI_QUEUE_AGENT_RUNS=false for local/demo use. 

// app/Listeners/RestoreLimenAiQueueAuthentication.php
public function handle(JobProcessing $event): void
{
    $userId = data_get($event->job->payload(), 'data.command.context.user_id');

    if ($userId !== null) {
        Auth::loginUsingId($userId);
    }
}

5. Browser drops slow local requests

Ollama can take 20s+. Raise OPENAI_TIMEOUT, add middleware that calls set_time_limit(120) on the Limen AI routes, and set LIMEN_AI_BROADCAST_DRIVER=null if you are not running a websocket server.

6. Too many tools on one agent

Local models degrade badly past ~10 tools. Split by audience: a public widget with 2 safe lookups, a staff agent with the full set, an admin agent with mutations behind approvals.

كل ما تحتاجه لبناء مساعد ذكي داخل تطبيق Laravel

الوكلاء (Agents)

حزم تعليمات + أدوات قابلة لإعادة الاستخدام (مثل: تتبع عام vs عمليات كاملة).

افعل

  • قسّم وكلاء: عام (guest) · موظف · أدمن
  • 5–10 أدوات max مع Ollama · 15–25 مع نماذج سحابية قوية

تجنّب

  • وكيل واحد بـ 20+ أداة — النموذج يختار غلط
  • وصف أداة غامض — لن تُستدعى أبداً
  • Skill فيها أداة مش موجودة في agent.tools
  • الاعتماد على الـ LLM للصلاحيات بدل authorize()
  • تعديل vendor مباشرة — استخدم stubs و config

الممارسة

وكيل = موظف له job description. اكتب instructions واضحة: متى ينادي أداة، متى يرد من knowledge، ومتى يقول «مش عارف».

],
