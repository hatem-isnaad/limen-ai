Troubleshooting

Common failures when building agents — symptom, cause, fix.

Cause: Tool not on agent's tools array, vague description, or skill/agent intersection empty.

Fix: Add tool key to agent config. Write description like “Call when user mentions order number.” Run php artisan limen-ai:tools to confirm registration.

Cause: Too many tools on one agent (especially local 7B–8B models).

Fix: Split agents per role. Keep public widget at 0–2 tools. See scaling guide.

Cause: authorize() returns false, or agent requires auth while widget is guest.

Fix: Public agent: guest_allowed: true and no privileged tools. Staff tools: separate agent on authenticated routes only.

Cause: Model cold start, low timeout, too many tools in context.

Fix: OPENAI_TIMEOUT=120, LIMEN_AI_QUEUE_AGENT_RUNS=false for local dev, reduce tools, run ollama serve.

Cause: Collection not attached to agent knowledge array, or chunks too long/vague.

Fix: Attach collection key to agent. Use 2–4 sentence factual chunks. Test with limen-ai:agent:test.

Cause: Tool in skill but not in agent tools — intersection must include both.

Fix: Add tool key to agent AND skill, or drop skill tools and list on agent only. See concepts (AR).

Official package reference
v1.2.2 · Laravel 11–13 · PHP 8.2+

Drop-in AI chat for Laravel — black-box simple

Install, set .env, add agents/tools/knowledge in config, embed the widget — chat replies automatically. No Laravel Gates in default mode. Tools use authorize() on BaseTool. Knowledge (FAQ/RAG) injects into every turn.

Black-box guide (5 min) Markdown guide GitHub

Black-box developer path

Everything a new developer needs — no framework internals, no Gate setup.

You change config + env. The package runs the agent loop.

Prepare a knowledge base (FAQ chunks), optional tools for lookups/actions, one Blade line for the widget. Users can chat immediately.

1 — Install

Shell
composer require limen-ai/limen-ai
php artisan limen-ai:install
php artisan migrate
php artisan config:clear

2 — Environment

.env
LIMEN_AI_DEFAULT_AGENT=app_assistant
LIMEN_AI_PROVIDER=openai
OPENAI_API_KEY=your-key

# Black-box auth (default) — no Gates

LIMEN_AI_REQUIRE_AUTH=false

No Gates

LIMEN_AI_AUTHORIZATION_MODE=simple — permission logic lives in tool classes.

Core principle

Every design decision follows one rule:

The LLM proposes actions. Laravel decides whether they are allowed and executes them safely.

User identity, permissions, data scoping, and side effects never come from model output — they come from Laravel auth, tool authorize() methods (simple mode), or Gates (optional gates mode).

Config-first

Define agents, tools, and workflows in PHP config — no redeploy to switch models or providers.

Host-owned logic

Business rules live in App\LimenAi\Tools\ and your services — the package stays domain-agnostic.

Test without LLM bills

FakeLlmProvider queues deterministic responses for fast CI and local development.

Quick start — add a tool

KB-only chat needs no tools. Add one when Laravel must execute an action.

Step 1 — Generate tool

Shell
php artisan limen-ai:make:tool GetOrderStatus --key=get_order_status

Step 2 — Implement authorize + handle

PHP
// extends LimenAi\Tools\BaseTool
public function authorize(array $input, ToolExecutionContext $context): bool
{
    return $context->userId() !== null; // false = blocked
}

public function handle(array $input, ToolExecutionContext $context): array
{
    return ['status' => 'ok', 'order_id' => $input['order_id']];
}

Step 3 — Register & attach to agent

PHP
'tools' => [
    'get_order_status' => [
        'class' => App\LimenAi\Tools\GetOrderStatusTool::class,
        'input_schema' => ['order_id' => ['type' => 'string', 'required' => true]],
    ],
],
'agents' => [
    'support_agent' => ['tools' => ['get_order_status']],
],

Step 4 — Test

Shell
php artisan limen-ai:doctor
php artisan limen-ai:agent:test support_agent --user=1 --message="Status of order 123?"

Architecture

Modular layers keep AI orchestration separate from your business logic.

User Message ↓ ConversationService ↓ AgentRuntime::run() ↓ ContextBuilder (auth, memory, knowledge, history) ↓ LlmProvider::chat() ↓ Tool call requested? ──No──→ Final response │ Yes ↓ ToolPipeline ├─ Authorization (Gates) ├─ Input validation ├─ Approval gate (if required) ├─ Idempotency check ├─ Execute host tool / HTTP integration └─ Audit + events ↓ LlmProvider (with tool result) → persist + broadcast

Runtime & orchestration

Agents, tools pipeline, workflows, memory, knowledge, UI components, observability.

Tools

Tools are Laravel classes or declarative HTTP integrations the LLM can invoke — always through authorization and validation.

Class-based tool

PHP
'get_shipment_status' => [
    'name' => 'Get Shipment Status',
    'class' => App\LimenAi\Tools\GetShipmentStatusTool::class,
    'input_schema' => [
        'shipment_id' => ['type' => 'string', 'required' => true],
    ],
    'authorization' => ['abilities' => ['shipments.read']],
    'confirmation' => false,
],

Tool pipeline guarantees

  • Authorization via Laravel Gates before execution
  • Schema validation on all LLM-provided arguments
  • Human approval pause for sensitive tools (confirmation: true)
  • Idempotency guards and SSRF validation on outbound HTTP
  • Audit logging with sensitive field redaction

Programmatic API

Run agents from controllers, jobs, or listeners — without the HTTP layer or Blade UI.

PHP
use LimenAi\Contracts\Runtime\AgentRuntime;
use LimenAi\Runtime\RunContextData;

$runId = app(AgentRuntime::class)->run(
    agent: 'example',
    conversationId: 'conv-' . $user->id,
    message: 'Summarize open tickets for today.',
    context: RunContextData::make(['user_id' => $user->id]),
);
RunContextData is server-derived

Always pass the authenticated user ID from Laravel — never from LLM output or client-supplied JSON.

Security

Defense in depth — the LLM never becomes your authorization layer.

Authentication (Laravel Guards) ↓ Agent authorization (abilities / simple mode) ↓ Server-derived RunContext (user ID) ↓ Prompt injection sanitization ↓ Tool authorization + validation ↓ Approval gate for sensitive tools ↓ Guest-safe tool enforcement ↓ Auto rate limiting on public widgets ↓ SSRF-safe HTTP + audit log

Guest widgets apply ThrottleAgentRequests automatically — no middleware publish required. See SECURITY.md for the full threat model.

Observability

  • trace_id — correlates run, LLM calls, and tool spans
  • Audit actions: agent.started, tool.completed, agent.failed
  • Usage metrics: prompt/completion tokens per provider/model
  • Export via GET /limen-ai/runs/{id}/observability
